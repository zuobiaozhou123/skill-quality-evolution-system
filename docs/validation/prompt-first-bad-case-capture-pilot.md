## 1. 试点 Skill

| 类别 | 暂定 Skill | 选择理由 |
|---|---|---|
| 客观可验 | `xlsx` | 公式、表头、行数和文件结构可直接复核，适合建立明确纠错样本。 |
| 开放式 | `brainstorming` | 结果没有单一标准答案，可验证“追加要求”与“否定方向”的边界。 |
| 路由冲突 | `requirements-analysis` + `prd-writer` | 两者能力相邻，可验证 Bad Case 归属于实际读取的 Skill，而不是模型预期的路由。 |

试点只通过临时符号链接读取现有 Skill，没有修改 `~/.codex/skills` 或用户级 Codex 配置。

## 4. 真实 Codex 试点

### 隔离方式

- 使用 `mktemp` 创建临时 `CODEX_HOME`、临时工作区、临时会话目录和临时 SQLite。
- 临时配置中注册 stdio MCP `record_bad_case`，指向隔离服务端口 `4327`。
- 工作区 `AGENTS.md` 仅引用审核过的短提示片段。
- 试点过程不写入仓库 `.runtime`，不修改正式 Skill 或全局用户配置。

### 有界尝试

1. 启动隔离后台，`GET /api/health` 返回 `{"status":"ok"}`。
2. 默认模型启动一条 `xlsx` 流程任务；等待超过 90 秒后，会话只有 `task_started` 和用户请求，没有模型消息、Skill 读取、工具调用或 `task_complete`。
3. 使用 `gpt-5.2` 发起最小连通性任务；等待超过 80 秒后仍停在 `task_started`，也没有模型消息或 `task_complete`。
4. CLI 同时记录远程插件目录同步的认证/网络告警；最小任务也未返回，因此不能证明该告警是唯一根因。

本轮没有形成一次完整的 Skill 交付，无法绑定“上一已完成轮次”，也无法真实调用 `record_bad_case`。本文不记录原始对话、会话 ID、凭证或临时路径。

## 6. 恢复后的复验步骤

1. 在隔离 `CODEX_HOME` 中注册本地 `record_bad_case` MCP，并启动指向临时会话与数据目录的后台。
2. 分别用三类暂定 Skill 完成一次交付，从本地 JSONL 校验实际 Skill、`threadId` 和已完成 `turnId`。
3. 每条负反馈前显式绑定上一轮元数据；补充、继、正面和新任务不绑定可采集引用。
4. 至少完成 10 条明确负反馈和 20 条非负反馈，否则一次误报就无法满足 `<= 5%`。
5. 从 MCP 调用、Capture Event、Bad Case、Delivery Drawer 四处交叉核对，记录每条的实际动作、关联正确性、治理播报数和澄清次数。
6. 仅当全部门槛达成时，将本文总签署更新为通过；不在本阶段启动 Skill 候选优化或修改正式 Skill。
