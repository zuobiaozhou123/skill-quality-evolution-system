# Skill 质量保障与自进化体系架构设计

## 1. 背景

Skill 写好并不等于长期有效。随着业务、规则、模型和 Skill 库本身持续变化，静态 Skill 会逐渐暴露出四类问题：创建质量不稳定、该调用时没有调用、调用后的执行效果退化，以及多个 Skill 之间重复或冲突。

本文基于“失败归因、部署反馈、受控优化”三类研究思路，设计一套覆盖 Skill 全生命周期的质量保障与自进化体系。第一阶段服务个人 Codex Skill 库，未来可平滑演进为团队及企业级治理平台。

## 2. 已确认的架构决策

1. **演进范围**：以个人版验证闭环，但核心对象和逻辑边界支持团队版、企业版演进。
2. **自动化边界**：系统可自动生成候选版本并运行评测，正式发布必须人工批准。
3. **反馈来源**：结合运行记录、人工失败案例、用户纠正和预设测试集。
4. **治理范围**：覆盖创建准入、路由质量、执行质量、库级治理和持续进化。
5. **总体结构**：采用“双回路 + 共享治理底座 + 人工发布门”。
6. **第一阶段形态**：采用本地模块化单体，不提前建设分布式平台。

## 3. 设计目标

这套体系需要持续回答六个问题：

1. 为什么要修改这个 Skill？
2. 失败是否真的应归因于 Skill？
3. 修改依据来自什么证据？
4. 候选版本解决了什么，又破坏了什么？
5. 它放回整个 Skill 库后是否仍然安全？
6. 为什么允许发布，以及出问题时如何恢复？

系统的目标不是追求最高自动化程度，而是建立一条可信、可验证、可审批、可回滚的持续进化链路。

## 4. 核心原则

- **证据先于修改**：失败日志不是修改指令，必须先形成可信证据并完成归因。
- **候选与生产隔离**：进化系统只能创建候选版本，不能直接修改正式版本。
- **评估与优化分离**：候选生成器不能决定自己的修改是否合格。
- **小步、可归因**：每轮只解决一类问题，并限制修改范围和编辑量。
- **最佳不等于最新**：正式运行指向最佳已批准版本，而不是最新生成版本。
- **局部提升不代表全局提升**：单 Skill 评测通过后，还要检查库级路由和冲突影响。
- **不确定时保持稳定**：证据不足、归因不清或评测波动时，保留原正式版本。

## 5. 总体架构

```text
┌────────────────────── 反馈来源 ──────────────────────┐
│ Codex 运行记录 │ 人工失败案例 │ 用户纠正 │ 固定测试集 │
└────────────────────────┬────────────────────────────┘
                         ↓
┌──────────────────── 证据与评测底座 ───────────────────┐
│ 原始 Run │ 结构化 Evidence │ Evaluation Case │ 可信等级 │
└────────────────────────┬────────────────────────────┘
                         ↓
┌────────────────────── 质量控制层 ─────────────────────┐
│                                                     │
│  单 Skill 质量回路             Skill 库治理回路       │
│  ────────────────             ────────────────       │
│  创建准入                       路由覆盖               │
│  失败归因                       静默绕过               │
│  候选修改                       重复与冲突             │
│  回归验证                       老化与依赖             │
│                                                     │
└─────────────────┬─────────────────┬─────────────────┘
                  ↓                 ↓
           单项质量报告       库级影响报告
                  └────────┬────────┘
                           ↓
┌──────────────────── 控制与发布层 ─────────────────────┐
│ 风险策略 │ 验证门 │ 人工审批 │ 版本晋级 │ 回滚 │ 审计 │
└────────────────────────┬────────────────────────────┘
                         ↓
┌──────────────────── 正式 Skill 运行库 ─────────────────┐
│ 只含已批准版本 │ 最佳版本指针 │ 历史稳定版本 │ 依赖关系 │
└────────────────────────┬────────────────────────────┘
                         ↓
                    新一轮运行反馈
```

系统由执行系统、进化系统和治理系统组成。执行系统负责使用正式 Skill 完成任务；进化系统负责从证据中提出并验证候选版本；治理系统负责风险控制、库级协调和最终发布。三个系统相互制约，任何一方都不能单独改写生产状态。

## 6. 五层职责

### 6.1 资产与运行层

维护 Skill 身份、正式版本、历史版本和依赖关系。Agent 只能加载已经批准的正式版本；运行过程在旁路留下调用和结果记录。

### 6.2 证据与评测层

统一承载运行轨迹、用户纠正、人工案例、业务结果、评测案例和评测结果。这一层独立于优化器，是系统判断“是否真的变好”的事实基础。

### 6.3 双质量回路

- **单 Skill 质量回路**：负责创建准入、失败归因、候选修改和回归验证。
- **Skill 库治理回路**：负责路由覆盖、静默绕过、重复冲突、依赖影响和长期老化。

### 6.4 控制与发布层

根据风险策略、质量门槛和人工审批决定候选版本是否晋级。正式发布必须保留上一稳定版本和完整决策记录。

### 6.5 人工治理台

集中呈现证据、归因、版本差异、单项评测和库级影响。人负责处理证据不确定、开放性结果、多 Skill 取舍和最终发布决策。

## 7. 核心领域对象

| 对象 | 定义 |
|---|---|
| Skill Asset | 一个可治理的能力单元，具有边界、所有者和风险等级 |
| Skill Version | Skill 的不可变版本快照，用于比较、发布和回滚 |
| Run | 一次真实调用及其执行结果 |
| Evidence | 从 Run、用户纠正或人工验收中提炼出的事实 |
| Evaluation Case | 可重复运行的正例、反例、边界例和失败复现例 |
| Change Proposal | 针对明确问题生成的候选修改及其理由 |
| Governance Issue | 跨 Skill 的重复、冲突、绕过、老化或依赖问题 |

一个完整的 Skill 资产不再只是一份 `SKILL.md`，而是：

```text
Skill 资产
= 可执行说明
+ 适用边界
+ 运行证据
+ 评测集
+ 版本谱系
+ 治理状态
```

## 8. 版本生命周期

```text
草稿
  ↓ 准入质检
候选版本
  ↓ 离线评测通过
待审批
  ↓ 人工批准
正式版本
  ↓ 被新版本替代
历史稳定版本

候选失败 → 拒绝缓冲区
正式异常 → 回滚到历史稳定版本
```

版本一旦产生便不可覆盖。一个 Skill 在一个运行环境中只能有一个正式版本；最新版本与最佳版本使用不同指针表达。

## 9. 双回路协作

### 9.1 单 Skill 质量回路

```text
运行反馈
→ 证据确认
→ 失败归因
→ 判断是否应修改 Skill
→ 生成受限候选版本
→ 问题复现与固定回归评测
→ 进入待审批或拒绝缓冲区
```

失败归因至少区分：Skill 内容缺失或错误、执行疏漏、路由问题、工具或环境故障、任务输入问题，以及证据不足。只有适合通过长期规则解决的问题，才能进入候选修改。

### 9.2 Skill 库治理回路

库级治理既可由候选发布事件触发，也可周期运行。它基于 Skill 清单、调用记录和路由评测，形成留用、改造、合并、拆分或停用建议。

任何候选版本发布前，都要检查是否造成新的漏触发、误触发、能力重叠、规则冲突、组合调用退化或依赖变化。

## 10. 质量保障模型

Skill 质量不压缩为单一总分，而是使用多维质量向量：

| 质量维度 | 核心问题 |
|---|---|
| 结构质量 | Skill 是否完整、清晰、可执行，职责是否分离 |
| 路由质量 | 该调用时是否调用，不该调用时是否保持沉默 |
| 执行质量 | 调用后是否真正改善任务结果 |
| 稳健质量 | 面对变体、边界和新场景时是否仍然有效 |
| 生态质量 | 是否与相邻 Skill 重复、冲突或破坏组合调用 |
| 运行质量 | 成本、时延、异常率和回滚能力是否可接受 |

候选版本只有在关键门槛全部通过、目标维度明确改善、非目标维度未超过退化容忍范围时，才可进入审批。高风险场景不能用其他维度的提升抵消安全退化。

评测信号的默认可信顺序为：业务系统客观结果、工具或 API 结果、用户明确纠正或人工验收、可复现测试案例、独立模型评审、执行 Agent 自我评价。模型判断可提供辅助解释，但不能单独决定发布。

## 11. 受控自进化引擎

自进化引擎采用三项逻辑职责分离：

```text
归因器 → 候选生成器 → 独立验证器
```

- **归因器**只创建结构化问题判断，无权修改 Skill。
- **候选生成器**依据明确目标、允许修改区域和编辑预算产生变更提案。
- **独立验证器**使用统一协议比较稳定版本与候选版本，不接受候选生成器的自我评价。

评测集分为问题复现集、固定回归集和隔离验证集。没有隔离验证集时，只能声明候选解决了已知案例，不能声明 Skill 整体能力提升。

系统采用文本学习率、验证门、拒绝编辑缓冲区、最佳版本指针和快慢更新分离。Skill 内容可以相对快速迭代；归因规则、评测协议、优化策略和风险门槛属于治理元规则，必须更慢更新并单独审批。

## 12. 异常与安全控制

默认安全策略如下：

```text
证据不足        → 不改
归因不确定      → 不改
评测持平        → 不发布
结果波动过大    → 不发布
库级冲突未解决  → 不发布
审批超时        → 保持原版本
线上表现下降    → 回滚并冻结
```

原始反馈进入长期评测集之前，必须完成敏感信息处理、完整性检查、可复现性确认和预期行为确认。一次模型自我反思、单次偶发纠正或外部工具故障不能自动成为永久规则。

## 13. 分阶段演进

### 13.1 个人版

采用本地文件、Git 和本地运行器，先跑通证据、候选、评测、审批和回滚。核心目标是验证反馈能否转成评测案例、候选修改能否稳定改善结果，以及人工能否基于差异报告完成决策。

### 13.2 团队版

增加中央 Skill 注册表、共享评测仓库、所有者和审批角色、统一运行采集、模型与环境对比，以及团队级冲突和依赖分析。

### 13.3 企业版

增加多租户与环境隔离、风险策略中心、分环境晋级、不可篡改审计、大规模事件采集，以及跨业务线的复用和隔离。

物理形态按以下路径演进：

```text
本地模块化单体
→ 共享控制面 + 分布式执行器
→ 多租户治理平台 + 企业策略中心
```

## 14. 第一阶段逻辑模块

| 模块 | 职责 |
|---|---|
| Skill Registry | 登记 Skill，维护正式版本和历史版本 |
| Observation Adapter | 导入运行记录、人工反馈和已有测试案例 |
| Evidence Inbox | 汇总可疑事件，支持确认、驳回和补充预期 |
| Case Repository | 管理正例、反例、边界例和失败复现例 |
| Quality Engine | 执行静态质检、路由测试、执行评测和版本对比 |
| Evolution Lab | 完成失败归因、候选生成和拒绝编辑记录 |
| Library Governor | 扫描死 Skill、重叠、冲突和库级影响 |
| Release Gate | 呈现证据和差异，支持批准、拒绝和回滚 |

以上是逻辑模块，第一阶段不拆为多个独立服务。

## 15. 第一阶段最小闭环

```text
选择一个已有 Skill
→ 登记当前稳定版本
→ 导入真实失败案例
→ 人工确认预期结果
→ 自动完成失败归因
→ 生成一个小幅候选修改
→ 基线与候选运行同一组评测
→ 检查相邻 Skill 路由影响
→ 生成差异报告
→ 人工批准或拒绝
→ 发布或保留原版本
```

首批验证宜选择三类 Skill：结果可客观判断的 Skill、偏开放性输出的 Skill，以及容易和相邻 Skill 发生路由冲突的 Skill。

## 16. 第一阶段非目标

- 自动批准和自动发布。
- 多个自治 Agent 互相辩论或投票。
- 实时流式采集所有会话。
- 企业级多租户和复杂审批流。
- 强行给所有开放性任务生成统一分数。
- 自动修改评测标准或风险策略。
- 一开始建设完整 Web 管理平台。
- 一开始扫描并优化整个 Skill 库。

## 17. 后续待决问题

以下问题有意留到下一阶段讨论，不在本架构文档中提前固化：

1. 第一批试点 Skill 的选择标准和具体名单。
2. Codex 运行记录可稳定提取哪些调用与结果信号。
3. 开放性任务的人工验收和模型评审应如何组合。
4. Evaluation Case、Evidence 和 Change Proposal 的最小数据结构。
5. 风险等级如何划分，以及不同等级对应哪些审批门槛。
6. 第一阶段成功指标及停止、扩展或调整条件。

本地交互形态已确定为轻量工作台，并已完成 V0 骨架：React 前台、Fastify 本地 API、SQLite 运行状态，以及 Git 可审查的 Registry/Evidence 文件。候选生成、评测和发布控制仍属于后续阶段。

## 18. 架构结论

本方案以证据为中心，以评测为约束，以候选版本为进化载体，以人工发布门控制风险，通过单 Skill 和 Skill 库两条回路完成持续质量保障。

第一阶段的任务不是证明 Skill 可以完全自治，而是证明它能够在不破坏稳定能力的前提下，被持续、可解释地改进。
