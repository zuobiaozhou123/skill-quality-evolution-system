# Prompt-first Bad Case 自动采集架构设计

## 1. 背景与目标

治理工作台 V0 已具备运行发现、Bad Case 确认、失败归因和 Evidence 资产化能力，但主要依赖人工从运行列表标记案例。这个入口要求用户离开生产对话后重新判断任务质量，既缺少完整交付上下文，也难以长期运行。

下一阶段把用户对上一轮交付的真实反馈作为主要采集信号。系统不要求 AI 对自己的交付做二次质检，也不在对话中播报治理状态。采集必须依附正常任务流程、保持极低上下文成本，并将不确定案例隔离在人工确认之前。

## 2. 已确认的设计决策

1. **信号来源**：只解释用户下一轮反馈，不增加 AI 自我质检。
2. **治理范围**：仅当上一轮实际调用过 Skill 时才进行反馈判定；普通 AI 回答质量不进入 Skill 治理。
3. **触发方式**：由极短系统提示片段触发 `record_bad_case`，不采用对话 Hook 作为主方案。
4. **承载方式**：个人验证期使用全局 `AGENTS.md`；正式形态由插件注入同一提示片段并注册记录工具。
5. **对话体验**：高置信判断静默执行；低置信判断最多澄清一次；不输出采集或治理状态。
6. **数据关联**：工具通过 Delivery Unit 引用关联完整上下文，不重传请求和交付全文。
7. **治理隔离**：自动采集只创建“待确认 Bad Case”，不能直接归因、资产化或修改 Skill。

## 3. 核心架构

```text
对话生产层
系统提示片段解释用户下一轮反馈
        ↓
采集工具层
record_bad_case 静默接收 Delivery Unit 引用和精简原因
        ↓
关联与存储层
关联上一请求、交付、实际 Skill 和用户反馈，完成去重与持久化
        ↓
治理工作台
展示完整交付单元，以“待确认”状态进入人工治理
        ↓
证据与进化链路
人工确认 → 归因 → Evidence → 后续候选与评测
```

### 3.1 对话生产层

系统提示片段只负责判断本轮用户反馈是否应触发采集。它不描述治理架构、数据结构或状态机，不要求模型重新评价自己的输出，也不承担持久化职责。

建议提示片段：

```text
仅当上一轮实际调用 Skill 且本轮明确否定、纠错或要求返工时，静默调用 record_bad_case；不做自评。疑似但不确定时，每个任务最多在正常回答末尾澄清一次；其他情况不处理，也不输出治理状态。
```

### 3.2 采集工具层

`record_bad_case` 是对话层唯一需要知道的治理能力。工具调用保持紧凑，只携带可定位上一轮交付的引用和从用户反馈中提炼的精简失败原因。字段约束、校验和默认行为由工具定义承担，不进入系统提示词。

### 3.3 关联与存储层

后台以 Delivery Unit 作为运行观察和治理之间的连接对象。一个 Delivery Unit 表示一次可判断的 Skill 交付，包含用户请求、AI 最终交付、实际调用的 Skill、会话与轮次引用，以及用户下一轮反馈。

请求和交付全文只保留在本地运行记录中。工具不得为了创建 Bad Case 而在模型上下文或参数中复制这些内容。后台根据引用读取完整交付，并负责去重、状态管理和失败重试。

### 3.4 治理工作台

“运行发现”应从会话摘要列表演进为 Delivery Unit 列表。用户判断一个案例时必须能同时看到：

- 用户请求；
- AI 最终交付结果；
- 实际调用的 Skill；
- 用户下一轮反馈；
- 系统为何判为候选 Bad Case；
- 当前采集与治理状态。

自动采集的记录统一进入“待确认”。用户仍可驳回误判、补充期望结果、完成失败归因并决定是否资产化。

## 4. 反馈判定规则

| 用户下一轮反馈 | 系统动作 |
|---|---|
| 明确否定、纠错或要求返工 | 静默创建待确认 Bad Case |
| 疑似不满意但含义不清 | 先完成当前任务，再在末尾澄清一次 |
| 补充要求或继续推进 | 不采集 |
| 接受结果或切换新任务 | 不采集 |

所有分支都以“上一轮实际调用过 Skill”为前置条件。高置信正面和高置信负面反馈均不追问。低置信澄清每个任务最多出现一次；用户没有回答时不再追问。

## 5. 数据流与状态边界

```text
Skill 交付形成 Delivery Unit
→ 用户给出下一轮反馈
→ 系统提示片段判断反馈含义
   ├─ 不触发：正常完成任务
   ├─ 低置信：正常完成任务后澄清一次
   └─ 高置信负面：静默调用 record_bad_case
→ 后台关联 Delivery Unit 并去重
→ 创建待确认 Bad Case
→ 工作台人工确认或驳回
```

一次负反馈只是待核实信号，不是永久证据，更不是 Skill 修改指令。只有经过人工确认和归因的案例，才可以进入 Evidence 与后续自进化链路。

## 6. 异常与安全策略

- `record_bad_case` 调用失败不能阻塞或改变当前回答，后台进入本地重试队列。
- 无法可靠关联 Delivery Unit 时不创建 Bad Case，只记录采集异常，禁止按时间猜测并写入错误证据。
- 同一反馈的重复调用按 Delivery Unit 引用去重。
- 采集、失败和重试状态只在治理工作台展示，不回写生产对话。
- 原始会话继续保留在本地运行记录中，不进入 Git；Evidence 仍遵循脱敏和人工资产化边界。

## 7. 分阶段承载

### 7.1 个人验证期

在全局 `AGENTS.md` 中放置同一条极短提示规则，并接入本地 `record_bad_case` 工具。目标是验证反馈判定、Delivery Unit 关联和工作台闭环，不追求跨平台覆盖。

### 7.2 正式形态

将提示片段、记录工具和配置作为同一插件版本发布。插件保证提示与工具成对存在，避免出现模型知道要记录但运行环境没有对应工具的情况。专用采集 Skill 不作为承载方式，因为它需要先被路由才能执行，存在循环依赖和漏触发。

## 8. 第一阶段成功标准

第一阶段采用准确率优先于召回率的策略：宁可漏掉模糊反馈，也不能污染 Skill 证据库。

| 维度 | 成功标准 |
|---|---|
| 触发准确性 | 明确否定、纠错、返工的采集率不低于 90%；正常补充和新任务误报率不高于 5% |
| 关联准确性 | 已创建 Bad Case 的 Delivery Unit 关联正确率为 100% |
| 对话体验 | 高置信反馈零治理播报；单任务最多澄清一次；采集失败不影响回答 |
| 上下文成本 | 系统提示片段约 100 个中文字符；工具不重传请求和交付全文 |
| 工作台可判断性 | 每条案例可查看请求、交付、实际 Skill、用户反馈、失败原因和状态 |

## 9. 验证框架

```text
反馈判定样本集
→ Delivery Unit 关联测试
→ 真实 Codex 对话端到端试点
```

判定样本至少覆盖明确否定、局部纠错、要求重做、补充要求、继续推进、正面反馈、新任务和模糊不满。端到端试点关注采集准确性、关联准确性、对话干扰和工作台可判断性，不在架构未落地前启动 Skill 候选优化测试。

## 10. 非目标

- 对每轮交付执行 AI 自我质检。
- 将所有普通 AI 质量问题纳入 Skill 治理。
- 在对话中展示 Bad Case 创建、重试或治理状态。
- 根据一次用户负反馈直接生成 Evidence 或修改 Skill。
- 用完整上下文复制换取更简单的工具调用。
- 第一阶段覆盖所有 AI 产品和对话入口。

## 11. 与现有 V0 的关系

现有 V0 的 Bad Case 状态机、Evidence 资产化和本地工作台继续保留。本文只替换主要采集入口并升级运行发现的信息单位：

```text
V0：会话摘要 → 人工标记 Bad Case
下一阶段：Delivery Unit → 用户反馈触发待确认 Bad Case
```

人工标记仍作为补录和纠错入口存在，但不再承担日常采集主路径。
